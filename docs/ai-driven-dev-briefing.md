# AI駆動開発ってなに？ 〜 tsubuyaki-board 演習に学ぶ導入の考え方 〜

> **対象読者**: これまでAIエージェントにコードを書かせた経験がない、社内の先輩・後輩・同僚。
> **目的**: 「AIに開発を任せる」ときに何が変わり、何を守れば安全に運用できるかを、本演習リポジトリを題材に説明する。

---

## 1. AI駆動開発とは

これまでのAI活用（ChatGPTに質問する、コード補完を使う）と、ここで言う「AI駆動開発」は少し違う。

- **チャット/補完**: 人間が手を動かす。AIは提案するだけ。
- **AI駆動開発**: AIエージェント（本演習では OpenAI の Codex CLI）が、要件を渡されると
  **自らファイルを編集し、テストを実行し、コミットまで行う**。人間はレビューと承認に回る。

つまりAIに「実行権限」を持たせる開発スタイル。ここで最初に浮かぶ疑問が次の節。

---

## 2. 一番大事な問い：「AIに何でもやらせて大丈夫？」

自律的にコマンドを叩けるということは、裏を返せば

- 誤って `rm -rf` してしまう
- `git push --force` で他人の変更を消してしまう
- `.env` の中身を読んで機密情報が漏れる

といったリスクも人間より速く・大量に起こしうるということ。

この不安に対する答えが **「ハーネス」**（安全装置一式）。本リポジトリはこのハーネスの実例そのもの。

---

## 3. ハーネスの仕組み：3層の安全装置

「AIへのお願い」だけに頼らず、**破ろうとしても物理的に破れない層**まで用意しているのがポイント。

| 層 | 何をするか | このリポでの実体 |
|---|---|---|
| ① プロンプト層 | AIに「これはやってはいけない」と言葉で約束させる | `AGENTS.md`（規範書）、`.codex/instructions.md`（補足） |
| ② 設定層 | AIツール自体の権限を絞る（承認要否・書き込み範囲・環境変数） | `.codex/config.toml` |
| ③ 物理層 | OS/コンテナレベルで実行自体を止める（言葉ではなく仕組みで防ぐ） | `scripts/run-codex.sh`（機密ファイルのマスク、規範ファイルの読み取り専用化）、`containers/codex-devbox/bin/*-guard.sh`（危険コマンドの実行拒否） |

**なぜ3層も用意するのか**：①は所詮「お願い」なので、AIの判断ミスやプロンプト経由の誘導で破られる可能性がある。③まで用意しておけば、①が機能しなくても最終的に危険操作は物理的にブロックされる。「AIを信用しない前提」で設計されている、と考えると分かりやすい。

具体例：`git push --force` や `git reset --hard` は、たとえAIがうっかり実行しようとしても、コンテナ内の wrapper スクリプトが `exit code 126` で即座に拒否する。

---

## 4. なぜTDD（テスト駆動開発）と組み合わせるのか

AIはコードを速く・大量に書けるが、その分「動くつもりで書いたが実は間違っている」コードにも気づきにくい。そこで役立つのがTDD。

- **先にテストを書かせる** → 「何ができれば正解か」を先に定義する
- **テストが通ったら初めて実装完了とみなす** → 人間は差分ではなく「テスト結果が緑かどうか」でレビューできる
- **Red（失敗）→ Green（成功）→ Refactor（整理）** のサイクルを型として与えることで、AIも人間も進捗を追いやすくなる

このリポで使っているツール（Javaの場合）：

| ツール | 役割 |
|---|---|
| JUnit 5 | テストフレームワーク本体 |
| Mockito | 依存をモック化し、対象だけを単体テスト |
| AssertJ | 読みやすいアサーション |
| MockMvc / `@DataJpaTest` | Web層・DB層それぞれの結合テスト |
| JaCoCo | テストカバレッジを計測し、閾値を満たさなければビルドを失敗させる |
| Checkstyle / SpotBugs | コードの書き方・潜在バグを機械的にチェック |
| `./mvnw verify` | 上記すべてを1コマンドで実行する統一入口（Red/Greenの判定装置） |

ポイントは「AIが自己申告する『できました』を信じるのではなく、**機械的に緑/赤で判定できる状態を作る**」こと。

## 5. 自分のチームで応用するには

技術スタックが変わっても、押さえるべき考え方は同じ。 柱は次の4つ。

1. **テスト**（何ができれば正解かを機械的に判定する）
2. **静的解析**（書き方の悪さ・潜在バグを機械的に検知する）
3. **カバレッジ計測**（テストが足りているかを数値で見る）
4. **実行権限の制御**（AIに何をどこまで自動でやらせるかの線引き）

| 役割 | 本リポ（Java/Spring） | TypeScript/React の場合 | PHP/WordPress の場合 |
|---|---|---|---|
| テストランナー | JUnit 5 | Vitest / Jest | PHPUnit |
| モック | Mockito | `vi.mock` / `jest.mock` | Brain Monkey / WP_Mock |
| 画面・結合テスト | MockMvc | React Testing Library | `WP_UnitTestCase` |
| カバレッジ | JaCoCo | Istanbul / c8 | Xdebug + PHPUnit |
| 静的解析 | Checkstyle + SpotBugs | ESLint + `tsc` | PHPStan / PHPCS |
| 実行権限の制御 | podman + guardスクリプト | Docker/Dev Containers + 同様のwrapper | 同左 |

つまり「Java用の特殊な仕組み」ではなく、**言語が変わってもツールを差し替えるだけで同じ設計思想が使い回せる**、ということが重要な学び。

---

## 6. まとめ

- AI駆動開発とは、AIに「実行権限」を持たせて自律的にコードを書かせるスタイル
- リスクは「ハーネス」で管理する。**お願い（プロンプト）だけでなく、物理的に止める仕組み**まで用意するのが安全運用の鍵
- TDDと組み合わせることで、AIの成果物を「気合と目視」ではなく「機械的な緑/赤判定」でレビューできる
- ここで使っているツールはJava固有ではなく、他言語でも同じ役割のツールに置き換えれば同じ設計を再現できる

### よくある質問

**Q. AIに何でも実行させて怖くないですか？**
A. 本演習のように「物理層まで含めた多層防御」を敷けば、想定外の操作は実行前にブロックされる。人間の確認が必要な操作（push、破壊的操作など）は自動化の対象外にする設計にできる。

**Q. テストを先に書かせると開発が遅くならないですか？**
A. AIがテストとコードの両方を書くため、人間が手で書くより体感の負荷は下がることが多い。むしろ「テストがない状態でAIに大量の変更をさせる」方がレビューコストが跳ね上がる。

**Q. 導入のハードルは高くないですか？**
A. 4本柱（テスト・静的解析・カバレッジ・実行権限制御）は既存のCIやLintの延長で組める。まずは「AIに自動でやらせてよい範囲」を明文化するところ（本リポで言う`AGENTS.md`）から始めるのがおすすめ。
